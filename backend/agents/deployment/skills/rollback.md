# 回滚方案 Skill

制定有效的回滚方案，确保部署失败时可快速恢复服务。

## When to Use

- 部署后出现严重故障，需要回滚到上一版本
- 部署验证不通过，需要回滚
- 需要制定回滚方案和回滚脚本
- 回滚后需要分析原因并优化方案

**Do NOT use when:**
- 部署成功，无需回滚
- 问题可通过热修复解决，不需要整体回滚

## Core Pattern

### Before

```markdown
部署失败 → 手动恢复 → 恢复不完整 → 数据不一致
```

### After

```markdown
触发条件判断 → 执行回滚脚本 → 验证恢复状态 → 记录并分析
```

## Quick Reference

| 操作 | 说明 | 要点 |
|------|------|------|
| 方案设计 | 确定触发条件、设计步骤、准备脚本 | 回滚步骤必须可自动化 |
| 回滚测试 | 测试脚本、验证效果、评估时间 | 部署前必须测试回滚方案 |
| 回滚执行 | 判断条件、执行操作、验证结果 | 执行前通知相关人员 |
| 回滚总结 | 分析原因、总结教训、优化方案 | 每次回滚必须有总结 |

## Implementation

### Step 1: 回滚方案设计

- 确定回滚触发条件（自动/手动）
  - 自动条件：服务不可用、健康检查失败、错误率超阈值
  - 手动条件：功能异常、数据错误、性能下降
- 设计回滚步骤，确保每步可逆
- 准备回滚脚本并测试

### Step 2: 回滚测试

- 在测试环境执行回滚脚本
- 验证回滚后服务恢复正常
- 评估回滚所需时间（目标：15分钟内完成）

### Step 3: 回滚执行

1. 确认回滚条件已触发
2. 通知相关人员（技术负责人、运维、业务方）
3. 停止当前版本服务
4. 恢复上一版本代码
5. 恢复数据库（如需要）
6. 启动服务并验证

### Step 4: 回滚总结

- 分析回滚原因（部署问题/代码缺陷/环境问题）
- 总结经验教训
- 优化回滚方案和部署流程

### 2.2 手动回滚条件
- 核心功能异常
- 数据不一致
- 性能严重下降

## 4. 回滚脚本
```bash
#!/bin/bash
# 回滚脚本

# 1. 停止服务
systemctl stop [服务名]

# 2. 恢复代码
cp -r /backup/[版本] /app/[应用]

# 3. 恢复数据库
mysql -u[用户] -p[密码] [数据库] < /backup/[备份文件]

# 4. 启动服务
systemctl start [服务名]

# 5. 验证服务
curl http://localhost:[端口]/health
```

## Common Mistakes

| 错误 | 原因 | 修正 |
|------|------|------|
| 回滚条件不明确 | 无法判断何时回滚 | 明确自动和手动触发条件 |
| 回滚脚本未测试 | 执行时才发现问题 | 部署前必须测试回滚脚本 |
| 回滚后不验证 | 假设回滚即恢复 | 回滚后必须验证服务、数据、功能 |
| 忘记通知相关人员 | 信息不透明 | 回滚前必须通知技术、运维、业务方 |
| 回滚后不总结 | 同样的问题反复出现 | 每次回滚必须分析原因并优化方案 |

## Quality Checklist

- [ ] 回滚条件明确，自动和手动条件已定义
- [ ] 回滚步骤清晰，每步可执行
- [ ] 回滚脚本可用，已测试验证
- [ ] 回滚验证充分，覆盖服务、数据、功能、性能
