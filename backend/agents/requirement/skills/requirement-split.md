## Overview

将需求文档按照阿里需求拆分方法论进行结构化拆分，输出标准化的Markdown文件。每个拆分后的需求条目保持最小颗粒度，确保AI能够独立读取和理解，同时维持完整的需求追溯链。

## When to Use

- 需求收集完成后，需要将原始需求文档拆分为可执行的细粒度条目
- 需求文档过于庞大，AI无法一次性理解全部内容
- 需要将Epic/Feature级别的需求拆解为User Story级别
- 需要为后续的设计、开发、测试阶段提供清晰的需求输入

**Do NOT use when:**
- 需求文档本身已经是细粒度的用户故事
- 需求还处于初步构想阶段，尚未形成文档
- 只是进行需求变更，而非整体拆分

## Core Pattern

### Before

```markdown
# 一个大型需求文档
包含多个模块、数十个功能点、复杂的业务规则混杂在一起
AI难以一次性理解和处理
```

### After

```markdown
# 拆分后的结构化需求目录
├── epic-001-用户管理/
│   ├── README.md              # Epic概览
│   ├── feature-001-注册登录/
│   │   ├── README.md          # Feature概览
│   │   ├── story-001-手机号注册.md
│   │   ├── story-002-邮箱注册.md
│   │   └── story-003-密码登录.md
│   └── feature-002-个人中心/
│       ├── README.md
│       ├── story-004-查看个人信息.md
│       └── story-005-修改头像.md
└── _meta/
    ├── traceability-matrix.md  # 需求追溯矩阵
    └── glossary.md             # 术语表
```

## Quick Reference

| 操作 | 说明 | 注意事项 |
|------|------|----------|
| 文档解析 | 读取原始需求文档，识别结构和层次 | 保留原始上下文 |
| 层次拆分 | Epic → Feature → User Story → Task | 每级保持独立可理解 |
| 颗粒度控制 | 单个Story控制在AI一次可读范围内 | 建议300-500字 |
| 格式标准化 | 统一输出为Markdown格式 | 遵循模板规范 |
| 追溯关联 | 建立父子关系和依赖映射 | 确保双向可追溯 |

## Implementation

### Step 1: 文档预处理

读取原始需求文档，进行结构识别和内容分析。

1. 读取文档全文，识别文档结构（章节、标题层级）
2. 提取关键信息：业务目标、功能模块、业务规则、约束条件
3. 识别文档中的术语和概念，建立术语表
4. 标记模糊或不完整的需求点，待后续澄清

### Step 2: 层次划分

按照阿里需求层次模型进行逐级拆分。

**层次定义：**

| 层次 | 说明 | 粒度标准 | 命名规范 |
|------|------|----------|----------|
| Epic（史诗） | 大型业务目标，通常跨多个迭代 | 对应一个业务域或产品模块 | `epic-{序号}-{名称}` |
| Feature（特性） | 可交付的功能集合，一个迭代内可完成 | 对应一个完整的功能集合 | `feature-{序号}-{名称}` |
| User Story（用户故事） | 用户视角的功能描述，单次开发可完成 | 满足INVEST原则 | `story-{序号}-{名称}` |
| Task（任务） | 技术实现细节，开发人员可直接执行 | 单人1-3天可完成 | `task-{序号}-{名称}` |

**拆分规则：**

1. **独立性（Independent）**: 每个Story应尽可能独立，减少对其他Story的依赖
2. **可协商性（Negotiable）**: Story不是合同，细节可以协商
3. **有价值（Valuable）**: 每个Story对用户或业务必须有价值
4. **可估算（Estimable）**: 能够估算工作量
5. **小规模（Small）**: 一个Story应在一次迭代内完成
6. **可测试（Testable）**: 必须有明确的验收标准

### Step 3: 用户故事编写

按照标准格式编写每个用户故事。

**编写规范：**

```
作为 [角色]
我想要 [功能]
以便 [价值/目的]
```

**验收标准格式（Given-When-Then）：**

```
Given [前置条件]
When [触发动作]
Then [预期结果]
```

**单个Story文档结构：**

1. 基本信息（编号、标题、所属Feature、优先级）
2. 用户故事描述
3. 验收标准（至少3条，覆盖正常流程、异常流程、边界条件）
4. 业务规则
5. 依赖关系
6. 验证要点

### Step 4: 输出标准化

将拆分结果输出为标准化的Markdown文件结构。

**输出目录结构：**

```
{output_dir}/
├── _meta/
│   ├── glossary.md              # 术语表
│   ├── traceability-matrix.md   # 需求追溯矩阵
│   └── split-summary.md         # 拆分总结报告
├── epic-{序号}-{名称}/
│   ├── README.md                # Epic概览文档
│   └── feature-{序号}-{名称}/
│       ├── README.md            # Feature概览文档
│       ├── story-{序号}-{名称}.md   # 用户故事
│       └── task-{序号}-{名称}.md    # 任务（可选）
```

### Step 5: 质量校验

对拆分结果进行质量检查。

1. **完整性检查**: 原始需求文档中的所有需求点是否都已覆盖
2. **一致性检查**: 拆分后的需求之间是否存在矛盾或冲突
3. **颗粒度检查**: 每个Story是否满足INVEST原则
4. **追溯性检查**: 是否建立了完整的父子关系映射
5. **可读性检查**: 每个Story文档是否在300-500字以内，AI可独立理解

## Templates

### Epic概览模板

```markdown
# Epic: {Epic名称}

## 基本信息
- **Epic编号**: EPIC-{序号}
- **所属业务域**: {业务域名称}
- **负责人**: {姓名}
- **创建日期**: {YYYY-MM-DD}
- **状态**: 待分析

## 业务目标
{描述这个Epic要达成的业务目标}

## 功能范围
| Feature编号 | Feature名称 | 优先级 | 状态 |
|-------------|-------------|--------|------|
| FEAT-{序号} | {名称} | P0/P1/P2 | 待拆分 |

## 依赖关系
- 上游依赖：{列出依赖的其他Epic或外部条件}
- 下游影响：{列出依赖此Epic的其他模块}

## 风险与约束
- {风险1}
- {约束1}
```

## Common Mistakes

| 错误 | 原因 | 修正方法 |
|------|------|----------|
| 拆分粒度过粗 | 一个Story包含多个独立功能点 | 按用户操作维度进一步拆分，确保每个Story只描述一个功能 |
| 拆分粒度过细 | 将技术实现细节当作Story | 合并相关的Task，保持Story的业务完整性 |
| 缺少验收标准 | 只描述功能，不说明如何验证 | 每个Story必须包含至少3条Given-When-Then格式的验收标准 |
| 忽略非功能需求 | 只拆分功能需求，遗漏性能、安全等 | 在Feature级别补充非功能需求的验收标准 |
| 追溯链断裂 | 拆分后无法回溯到原始需求 | 维护追溯矩阵，确保每个Story都能追溯到原始REQ编号 |
| Story之间强依赖 | 拆分后Story必须按固定顺序执行 | 重新审视拆分方式，尽量减少Story间的依赖关系 |
| 文档过大 | 单个Story文档超过1000字 | 精简描述，将详细设计移至设计阶段，Story只保留业务描述 |

## Quality Checklist

- [ ] 原始需求文档中的所有需求点已覆盖
- [ ] 每个Story满足INVEST原则
- [ ] 每个Story包含完整的验收标准（至少3条）
- [ ] 每个Story文档在300-500字以内
- [ ] 追溯矩阵完整，每个Story可追溯到原始需求
- [ ] 术语表完整，专业术语有明确定义
- [ ] Epic/Feature/Story层次关系清晰
- [ ] 依赖关系已标注，无循环依赖
- [ ] 待澄清事项已记录

## Dependencies

- **Before**: 需求收集阶段完成，已有结构化的需求池或需求文档
- **After**: 输出拆分后的细粒度需求文档，供需求分析、设计、开发阶段使用
