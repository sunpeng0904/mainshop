## Overview

在需求阶段建立SDD（Software Design Document，软件设计说明书）的规范约束，定义SDD的结构标准、内容要求和质量基线。此规范作为设计阶段的输入约束，确保设计产出物符合阿里标准。

## When to Use

- 需求分析完成后，需要为设计阶段定义SDD编写规范
- 项目需要统一设计文档的标准和格式
- 需要建立从需求到设计的文档衔接规范
- 需要明确SDD各章节必须覆盖的内容范围

**Do NOT use when:**
- 项目已有完善的SDD规范且无需更新
- 处于需求收集阶段，尚未完成需求分析

## Core Pattern

| 维度 | 说明 | 产出 |
|------|------|------|
| 文档结构规范 | 定义SDD章节层级和必填/选填章节 | SDD结构标准 |
| 内容约束规范 | 定义每个章节必须覆盖的内容要素 | 内容要素清单 |
| 质量基线规范 | 定义SDD的质量评审标准 | 质量检查清单 |
| 追溯规范 | 定义SDD与SRS的追溯映射关系 | 追溯映射模板 |

## Implementation

### Step 1: 确定SDD文档体系

根据项目规模确定SDD的分层体系。

**阿里SDD分层标准：**

| 层级 | 名称 | 英文 | 说明 | 适用场景 |
|------|------|------|------|----------|
| L1 | 概要设计说明书 | HLD (High-Level Design) | 系统级架构设计，模块划分，接口定义 | 所有项目必须 |
| L2 | 详细设计说明书 | LLD (Low-Level Design) | 模块级详细设计，类图，序列图，数据流 | 中大型项目必须 |
| L3 | 数据库设计说明书 | DBD (Database Design) | 数据库表结构，索引，存储过程 | 有数据库的项目必须 |
| L4 | 接口设计说明书 | IFD (Interface Design) | API详细定义，协议规范，报文格式 | 有对外接口的项目必须 |

### Step 2: 定义SDD结构规范

为每个层级定义标准章节结构和必填/选填标记。

**HLD（概要设计）结构规范：**

```
1. 引言（必填）
   1.1 编写目的（必填）
   1.2 读者对象（必填）
   1.3 术语与缩略语（必填）
   1.4 参考文档（必填）
2. 系统概述（必填）
   2.1 系统目标（必填）
   2.2 系统约束（必填）
   2.3 设计原则（必填）
3. 架构设计（必填）
   3.1 架构风格选型（必填）
   3.2 系统上下文图（必填）
   3.3 分层架构设计（必填）
   3.4 模块划分（必填）
   3.5 部署架构（必填）
4. 模块设计（必填）
   4.x 模块N概述（必填）
       4.x.1 模块职责（必填）
       4.x.2 对外接口（必填）
       4.x.3 依赖关系（必填）
5. 数据设计（必填）
   5.1 数据模型概览（必填）
   5.2 核心实体关系（必填）
   5.3 数据流设计（必填）
6. 接口设计（必填）
   6.1 外部接口（必填）
   6.2 内部接口（必填）
   6.3 第三方接口（选填）
7. 非功能设计（必填）
   7.1 安全设计（必填）
   7.2 性能设计（必填）
   7.3 高可用设计（必填）
   7.4 可扩展性设计（选填）
8. 风险与对策（必填）
9. 附录（选填）
```

**LLD（详细设计）结构规范：**

```
1. 引言（必填）
   1.1 编写目的（必填）
   1.2 设计范围（必填）
2. 模块详细设计（必填）
   2.x 模块N详细设计
       2.x.1 类设计（必填）
       2.x.2 序列图（必填）
       2.x.3 状态图（选填）
       2.x.4 算法设计（选填）
       2.x.5 异常处理（必填）
3. 数据库详细设计（必填）
   3.1 表结构设计（必填）
   3.2 索引设计（必填）
   3.3 存储过程（选填）
   3.4 数据迁移方案（选填）
4. 接口详细设计（必填）
   4.x 接口N详细定义
       4.x.1 请求报文（必填）
       4.x.2 响应报文（必填）
       4.x.3 错误码（必填）
       4.x.4 业务规则（必填）
5. 关键流程设计（必填）
   5.x 流程N
       5.x.1 流程图（必填）
       5.x.2 时序图（必填）
       5.x.3 异常分支（必填）
```

### Step 3: 定义内容要素规范

为每个章节定义必须包含的内容要素和编写标准。

**内容要素规范示例：**

| 章节 | 必须要素 | 编写标准 | 与SRS映射 |
|------|----------|----------|-----------|
| 系统目标 | 业务目标、技术目标、约束条件 | 必须引用SRS中的业务需求编号 | SRS §2.1 |
| 架构设计 | 架构图、分层说明、技术选型理由 | 必须包含架构图，使用C4模型或4+1视图 | SRS §3 |
| 模块设计 | 模块职责、接口清单、依赖关系 | 每个模块必须对应SRS中的功能模块 | SRS §3.x |
| 数据设计 | ER图、表清单、字段说明 | 必须标注主键、外键、索引 | SRS §6 |
| 接口设计 | URL、方法、请求/响应格式 | 必须使用OpenAPI 3.0或等效格式 | SRS §5 |
| 安全设计 | 认证方案、授权方案、加密方案 | 必须引用安全需求编号 | SRS §4.2 |

### Step 4: 定义质量基线规范

建立SDD的质量评审标准。

**质量维度与基线：**

| 维度 | 基线要求 | 权重 |
|------|----------|------|
| 完整性 | 覆盖SRS中100%的功能需求和非功能需求 | 30% |
| 一致性 | 设计方案与SRS需求描述无矛盾 | 20% |
| 可实现性 | 设计方案技术可行，有明确的实现路径 | 20% |
| 规范性 | 符合文档结构规范，术语统一 | 15% |
| 可追溯性 | 每个设计元素可追溯到SRS需求编号 | 15% |

### Step 5: 建立追溯映射规范

定义SDD与SRS之间的追溯关系模板。

```markdown
# SDD-SRS追溯矩阵

| SRS需求编号 | SRS需求名称 | HLD章节 | LLD章节 | DBD章节 | IFD章节 | 设计状态 |
|-------------|-------------|---------|---------|---------|---------|----------|
| REQ-001 | 用户注册功能 | §4.1 | §2.1 | §3.1 | §4.1 | 已设计 |
| REQ-002 | 用户登录功能 | §4.1 | §2.2 | §3.1 | §4.2 | 已设计 |
| NFR-001 | 响应时间<2s | §7.2 | - | §3.2 | - | 已设计 |
```

## Quality Checklist

- [ ] SDD文档体系已确定（HLD/LLD/DBD/IFD）
- [ ] 每个层级的章节结构已定义，标注了必填/选填
- [ ] 每个章节的内容要素已明确
- [ ] 质量基线已建立，包含评审维度和权重
- [ ] SDD与SRS的追溯映射关系已定义
- [ ] 版本管理规范已明确
- [ ] 术语表与SRS保持一致
- [ ] 规范约束文档已通过评审

## Common Mistakes

| 错误 | 原因 | 修正方法 |
|------|------|----------|
| SDD与SRS脱节 | 设计阶段未参考SRS需求 | 建立强制追溯矩阵，每个设计元素必须映射到SRS需求 |
| 章节结构随意 | 没有预先定义SDD规范 | 在需求阶段就确定SDD结构规范，设计阶段严格执行 |
| 只有HLD没有LLD | 低估了详细设计的重要性 | 根据项目规模确定必须产出的SDD层级 |
| 质量标准模糊 | 没有建立量化评审标准 | 定义明确的质量维度和权重，使用评分制评审 |
| 忽略非功能设计 | 只关注功能实现 | 在SDD规范中将非功能设计设为必填章节 |

## Dependencies

- **Before**: 需求分析完成，SRS文档已产出
- **After**: 输出SDD编写规范约束，供设计阶段作为编写基线
